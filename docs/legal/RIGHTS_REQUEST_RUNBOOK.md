# 열람·삭제 요청 및 사고 대응 준비 절차

**내부 운영 초안. 실제 요청 창구·처리 SLA·물리 삭제 기능은 아직 완성되지 않았습니다.**

## 요청 처리

1. [미정: 담당 부서·연락처]에서 사건 번호·접수 시각·요청 종류를 기록합니다. 처음부터 신분증 원본 등 과도한 자료를 요구하지 않습니다.
2. 로그인 확인·등록 연락처·적법한 대리권 등 요청에 비례한 수단을 정해 본인 여부를 확인합니다. 이 과정에서 다른 사용자의 자료 존재를 드러내지 않습니다.
3. 계정 UUID에서 작품·임베딩·탐지·증거·알림·결제 연결·신고·소유권·소셜·첨부·감사·백업까지 범위를 조사합니다. 타인의 상품/공유 증거가 함께 있는지 확인합니다.
4. 적용 법령에 따른 기한, 허용/제한 사유, 별도 보존 근거와 종료일을 담당자가 확인합니다. 처리 불가·부분 처리도 사유와 이의 경로를 남깁니다.
5. 열람은 요청자 정보와 제3자 정보를 구분해 최소한으로 제공하는 기능을 구현합니다. 현재 전용 일괄 내보내기 API는 없습니다.
6. 삭제는 먼저 재수집·스캔·메일 등 후속 처리를 멈추고 세션 회수·결제 관계를 검토합니다. 그 뒤 승인된 범위의 DB·S3·파생물·큐·캐시를 처리하는 절차를 구현합니다. 현재 soft delete만 실행하고 “모든 개인정보가 삭제됐다”고 통지하지 않습니다.
7. 백업에 즉시 반영하기 어려운 항목은 보존·접근 제한·복원 후 재삭제 절차와 최종 파기 시점을 정합니다. 삭제 완료 검증·일부 보존·공급자 처리 결과를 구분해 알립니다.

사건 기록에는 접수/검증/범위/담당자/근거/조치/검증/통지/재검토일을 남기되, 원래 삭제 대상의 비밀값이나 자료 전문을 감사 로그에 복제하지 않습니다. 요청 로그 자체의 보유기간도 확정해야 합니다.

## 사고 대응

발견 → 접근·전파 억제 → 증거 최소 보존 → 영향 범위 확인 → 적용 통지·신고 의무 및 기한 판단 → 복구·재발 방지 순서의 운영 절차를 준비합니다. 비밀 키 노출·공개 버킷·원본 파일 유출 등을 가정해 역할별 대응을 훈련합니다. 모든 사고에 동일한 법정 시간 기준이 적용된다고 단정하지 않습니다.

현재 확인한 기준 자료는 [개인정보위 유출등 대응 안내서 2026.9. 게시](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=G010030030&nttId=12465)입니다. 첨부 안내서와 실제 법령·사업 규모·피해 유형을 담당자가 검토하고 연락망·판단 기록·실행 시간을 확정해야 합니다. 이번 작업에서 사건 접수, 삭제, 외부 통지 또는 신고는 하지 않았습니다.
