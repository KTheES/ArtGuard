## 4. 비기능 기준

측정은 격리된 로컬 환경, 단일 클라이언트, warm-up 3회 후 30회 요청으로 수행한다. 로컬 개발기 측정값이며 운영 SLO로 해석하지 않는다.

| --- | --- | --- | --- |
| N1 | Health 응답시간 | 30회 중 p95 ≤ 200 ms, 최대 ≤ 500 ms, 5xx 0 | ✅ PASS — p50 39.09 ms, p95 69.98 ms, 최대 103.85 ms, 5xx 0 |
| N2 | 작품 목록 응답시간 | 인증 요청 30회 중 p95 ≤ 500 ms, 최대 ≤ 1,000 ms, 5xx 0 | ✅ PASS — p50 29.93 ms, p95 54.61 ms, 최대 92.53 ms, 5xx 0 |
| N3 | 탐지 목록 응답시간 | 인증 요청 30회 중 p95 ≤ 500 ms, 최대 ≤ 1,000 ms, 5xx 0 | ✅ PASS — p50 36.73 ms, p95 129.94 ms, 최대 257.61 ms, 5xx 0 |

| N5 | 탐지 목록 SQL 호출 수 | 요청당 ≤ 6회, `size=1`→`size=20` 증가량 ≤ 1회 | ✅ PASS — size 1·20 모두 3회; 증가량 0 |

응답시간은 클라이언트에서 HTTP 전체 경과 시간을 측정한다. SQL 호출 수는 PostgreSQL `pg_stat_statements`를 요청 직전 초기화하고 애플리케이션 SQL의 호출 합계를 집계한다. Flyway, 측정 쿼리, `pg_stat_statements` 자체 쿼리와 health probe는 제외한다.

응답시간의 판정값은 하나의 `.NET HttpClient` 연결을 재사용한 결과다. 진단용 `Invoke-WebRequest` 1차 측정에서는 Health p95가 282.35 ms로 기준을 넘었지만 작품 122.78 ms, 탐지 129.67 ms는 통과했다. 셸 cmdlet 생성 비용을 분리하기 위해 같은 warm-up/30회 조건을 유지하고 연결 재사용 측정을 수행했으며 두 결과를 모두 보존한다.

## 실행 중 환경 복구 기록

- 첫 Gradle 실행은 샌드박스의 캐시/JDK 접근 제한으로 실패했다. JDK 21과 기존 Gradle 캐시를 명시한 뒤 `--rerun-tasks`로 실제 재실행하여 통과했다.
- 첫 통합 실행은 환경 `PATH`의 잘못된 리터럴 항목 `$env:PATH`와 중지된 Docker 때문에 초기화 실패했다. 해당 항목만 제거한 프로세스 환경으로 재실행했다.
- Docker Desktop 4.44.3은 stale `dockerInference` reparse endpoint 때문에 시작하지 못했다. Docker 이미지·볼륨은 유지하고 `AppData\Local\Docker\run`만 `run.stale-20261001-1700`으로 이동해 복구했다.
- 위 환경 실패는 애플리케이션 테스트 실패와 구분하며, 최종 결과는 캐시 결과가 아닌 실제 재실행 XML을 집계했다.
