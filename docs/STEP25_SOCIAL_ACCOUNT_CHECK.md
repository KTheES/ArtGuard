# STEP 25 소셜 프로필 통제 확인 — 수동 검토

사용자가 지정한 HTTPS 프로필에 일회용 공개 코드를 게시하고 관리자가 해당 페이지를 직접 확인하는 API입니다. OAuth 또는 소셜 서비스 API 인증은 아닙니다. 서버는 제출 URL을 방문하지 않으며 외부 계정에 게시하지 않습니다. 이번 개발에서도 실제 프로필 접속·게시·확인은 하지 않았습니다.

## 흐름

1. 이메일 인증한 사용자가 `POST /api/v1/social-checks`에 `{"profileUrl":"https://example.com/my-profile"}`를 제출합니다.
2. 응답의 challenge를 해당 프로필 소개 등 관리자가 확인할 수 있는 위치에 게시합니다. 코드는 공개 확인용이며 로그인 비밀값이 아닙니다. 인증 대기 유효기간은 24시간입니다.
3. 관리자는 `GET /api/v1/admin/social-checks`에서 대기 목록을 조회합니다. 여기에는 challenge가 제공되지 않습니다.
4. 관리자는 해당 URL이 요청한 계정의 실제 프로필인지 확인한 뒤 프로필에서 읽은 전체 코드를 제출합니다.
5. `PATCH /api/v1/admin/social-checks/{id}`에 `{"version":0,"approved":true,"observedCode":"ArtworkGuard-...","profileChecked":true,"reason":"프로필과 코드를 확인함"}`를 전달합니다. 반려 시 approved=false와 사유를 제출합니다.
6. 사용자는 `GET /api/v1/social-checks?page=0&size=20`에서 이력을 조회하고 `PATCH /api/v1/social-checks/{id}/revoke`에 `{"version":1}`을 보내 철회할 수 있습니다.

관리자 확인은 그 시점의 프로필 게시 권한에 대한 수동 검토 기록입니다. VERIFIED는 30일간 유효하고 이후 EXPIRED로 조회됩니다. 대기 요청도 24시간이 지나면 EXPIRED로 조회되며 더 이상 승인할 수 없습니다. 만료는 조회 시 계산하므로 별도 만료 감사 이벤트를 생성하지 않습니다. 프로필 양도·이름 변경·운영자 변경은 자동 감지하지 않습니다. 같은 사람이 소유한 모든 프로필을 식별하거나 여러 마켓의 판매자와 연결하지 않습니다. 작품의 저작권 소유나 플랫폼 공식 인증도 의미하지 않습니다.

## 제한과 기록

시작 요청은 사용자당 분당 1회, 유효한 대기는 최대 5개입니다. 같은 사용자가 같은 정규화 URL에 대기·유효 인증을 가진 동안 새 요청을 만들 수 없습니다. URL의 호스트 대소문자·기본 포트는 정규화하지만 경로 별칭·핸들 변경·서로 다른 사용자의 대리 운영을 하나의 신원으로 합치지는 않습니다. 지원 플랫폼을 자동 판별하지 않으므로 관리자가 해당 URL의 성격과 게시 위치를 직접 판단해야 합니다.

관리자 역할은 JWT와 현재 DB에서 검사하고 자기 요청은 승인할 수 없습니다. 코드·URL·소유자·발급 시각은 변경할 수 없으며 오래된 version의 검토·철회는 충돌 처리합니다. 승인 시 코드 일치와 미만료 조건을 SQL에서도 검사합니다. 철회 및 검토 내역은 V23 감사 이벤트에 상태와 행위자 ID로 남깁니다. 기존 작품·신고·소유권 자료 기능의 권한을 자동 확대하지 않습니다.

URL은 HTTPS·기본 포트만 허용하고 query·fragment·user info는 거절합니다. URL 문자열의 형식 검증은 사이트의 신뢰성 검증이 아닙니다. 향후 화면은 URL·검토 사유를 이스케이프하고 외부 링크를 명시적으로 표시해야 합니다. 원격 자동 수집이나 클릭 자동화는 구현하지 않았습니다.

## 검증과 다음 단계

서비스·인증/역할·요청 검증 단위 테스트를 추가했습니다. PostgreSQL 통합 테스트에는 V23 적용, URL/사용자 범위, 코드 불일치, 일회 검토, 철회, 만료 및 감사 기록을 포함했습니다. Docker 부재로 DB 통합 검증은 미완료입니다. 프런트엔드 화면과 OAuth 연동도 포함되지 않습니다.
