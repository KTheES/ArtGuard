# STEP 24 판매자 분석 API

판매자별 탐지 수, CONFIRMED/NEW 수, 상품 수, 작품 수, 창작자 수, 마켓 수, 검토 우선순위 점수, 최초·최근 탐지 시점을 집계합니다. 이번 단계는 백엔드 API이며 프런트엔드 화면은 포함하지 않습니다.

## 조회

- `GET /api/v1/sellers/intelligence?marketplace=ALIEXPRESS&page=0&size=20`: JWT 사용자 본인의 작품에 대한 집계.
- `GET /api/v1/admin/sellers/intelligence?page=0&size=20`: 관리자 전용 전체 활성 사용자 집계. JWT ADMIN 권한과 DB의 현재 관리자 상태를 모두 확인합니다.

marketplace는 선택 사항이며 기존 마켓 코드 enum을 사용합니다. page는 0~100000, size는 1~100입니다. 점수 내림차순 → 최근 탐지 내림차순 → 판매자 ID 순으로 정렬합니다. 응답은 items, totalElements, totalPages, page, size, scope, scoreVersion, scoreMeaning을 포함합니다. 건수가 없는 조회는 빈 목록입니다.

## 집계 의미와 범위

탐지 테이블의 작품·상품 쌍을 집계하므로 반복 스캔 횟수나 증거 스냅샷 수를 중복 계산하지 않습니다. NEW와 CONFIRMED만 포함하며 DISMISSED, 삭제된 작품, 비활성 사용자의 작품, MOCK 마켓은 제외합니다. 상품이 제거되거나 마켓 수집이 비활성화돼도 과거 탐지 기록은 집계에 남습니다.

일반 사용자 결과에는 다른 창작자의 수나 탐지 정보가 포함되지 않습니다. 따라서 결과가 있는 판매자의 creatorCount는 1입니다. 전역 창작자 수는 관리자 API에서만 제공합니다. firstSeen/lastSeen은 현재 조회 범위에 남아 있는 탐지의 최초·최근 발견 시점이며, 판매자 계정 생성일이나 마지막 판매 시점이 아닙니다.

판매자는 내부 sellerId(마켓별 외부 판매자 ID)로 구분합니다. 동일 이름·외부 ID만으로 마켓 간 판매자를 합치지 않습니다. 현재 데이터 모델에서는 marketplaceCount가 1입니다. 마켓을 넘는 동일 운영자 연결은 별도 식별 근거가 필요하며 아직 구현하지 않았습니다. 상품의 현재 판매자 연결을 사용하므로 향후 판매자 변경 이력을 도입하면 과거 귀속 방식도 별도 검토해야 합니다.

## 점수

`riskScore = min(100, 10 × confirmedCount + 2 × newCount)`

버전은 `review-priority-v1`입니다. 이 값은 검토 순서를 정하기 위한 초기 휴리스틱이며 법적 침해 확률·검증된 위험도·판매자의 위법 판단이 아닙니다. 관리자와 일반 사용자는 집계 범위가 달라 점수도 다를 수 있습니다. NEW가 많거나 특정 창작자의 작품이 많으면 점수가 커질 수 있습니다. 탐지를 DISMISSED로 변경하면 다음 조회에서 제외됩니다.

## 검증 및 남은 작업

인증, 관리자 접근 차단, JWT 소유자 범위 전달, 비활성·권한 철회 차단, 페이지 입력 검증을 단위 테스트합니다. PostgreSQL 집계 통합 테스트에는 다른 사용자·삭제 작품·MOCK·DISMISSED 제외, 동명 판매자 분리, 정렬·페이지·점수 상한을 포함했습니다. 현재 Docker 환경을 사용할 수 없어 SQL 통합 테스트 실행은 미완료입니다. 큰 데이터셋에서의 쿼리 성능 검증도 별도로 필요합니다.

다음 개발 항목은 STEP 25 부정 사용 방지입니다. 실제 AI 데이터·임계값 보정과 운영 인프라 검증은 계속 별도 미완료 항목입니다.
