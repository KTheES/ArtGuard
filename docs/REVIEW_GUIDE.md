# ArtworkGuard Pull Request 리뷰 가이드

## 1. 결정 사항 및 배경 (ADR)

리뷰의 차단 여부를 명확히 전달하기 위해 모든 실행 가능한 피드백은 `[MUST]` 또는 `[SHOULD]`로 시작한다. 취향 차이를 결함처럼 표현하지 않고, 문제의 조건·영향·권장 해결 방향을 함께 남긴다.

## 2. 아키텍처 설계

```mermaid
flowchart TD
    D[PR diff] --> S{보안·정확성·데이터 손실·회귀?}
    S -->|예| M[[MUST] 병합 전 해결]
    S -->|아니오| O{유지보수·성능·문서 개선?}
    O -->|예| H[[SHOULD] 권고]
    O -->|아니오| A[질문 또는 승인]
    M --> V[수정 및 재검증]
    H --> F[현재 또는 후속 반영]
```

리뷰는 최소한 동작 정확성, 보안·개인정보, 테스트·운영성 관점으로 확인한다. 과제 증거용 리뷰에서도 의미 없는 코멘트 수 채우기는 하지 않는다.

## 3. API 명세

리뷰 코멘트 형식은 다음과 같다.

```text
[MUST] 짧은 제목
조건: 어떤 입력·상태에서 발생하는가
영향: 사용자·데이터·운영에 어떤 문제가 생기는가
제안: 최소 수정 방향 또는 검증 방법
```

```text
[SHOULD] 짧은 제목
근거: 현재 코드의 유지보수·성능·가독성 문제
제안: 개선 방향과 기대 효과
```

## 4. 트러블슈팅 가이드

- 코드 줄에 연결할 수 있으면 인라인 코멘트를 사용하고, 전체 설계 문제는 PR 종합 리뷰에 남긴다.
- 재현할 수 없는 의심은 단정하지 않고 질문으로 남긴다.
- 해결된 `[MUST]`는 수정 커밋·테스트 결과를 확인한 뒤에만 Resolve한다.
- 리뷰 본문과 첨부 로그에 토큰·비밀번호·개인정보·로컬 절대 경로를 포함하지 않는다.
- 작성자가 자신의 PR을 리뷰할 때는 GitHub 승인이 아니라 `COMMENT` 리뷰로 자체 점검임을 명시한다.

## 5. 회의 노트 및 액션 아이템

이번 협업 규칙 적용 시 다음 세 관점의 구조화된 자체 리뷰를 남긴다.

| 관점 | 태그 | 확인 내용 |
| --- | --- | --- |
| 데이터 계약 | `[MUST]` | 잘못된 DORA JSON이 조용히 잘못 표시되지 않는지 |
| 입력 보안 | `[MUST]` | 외부 URL·자격증명·민감정보 노출 가능성이 없는지 |
| 공급망·운영 | `[SHOULD]` | CDN 의존성과 공개 대시보드 운영 정책이 명확한지 |

## 6. FAQ 및 Onboarding

### 리뷰 세 건은 승인 세 건을 뜻하나요?

아니다. 리뷰 피드백 세 건과 서로 다른 사람의 승인 세 건은 다르다. 현재 단일 소유자 저장소에서는 자체 `COMMENT` 리뷰를 증거로 남길 수 있지만, 실제 보호 규칙의 승인은 다른 협업자가 수행해야 한다.

### 수정이 끝난 `[MUST]`는 삭제하나요?

삭제하지 않는다. 수정 커밋과 해결 답변을 남겨 검토 이력을 보존한다.

### 사소한 개선도 반드시 태그를 붙이나요?

실행을 요청하는 피드백에는 붙인다. 단순 칭찬이나 확인 질문은 태그 없이 남길 수 있다.
