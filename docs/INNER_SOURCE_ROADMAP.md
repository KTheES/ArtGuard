# ArtworkGuard Inner Source 도입 로드맵

## 목표

공개 OSS 운영 방식을 조직 내부 협업에도 적용해 팀 경계를 넘는 재사용과 기여를 늘리고, 소유권과 품질 기준을 유지합니다. 공개 저장소에는 공개 가능한 코드와 문서만 두며 고객 데이터, 내부 인프라 정보, 비밀값은 포함하지 않습니다.

## 운영 원칙

- **Open by default, private when necessary**: 공개 가능한 설계·코드·결정은 검색 가능한 저장소에 둡니다.
- **명확한 소유권**: 영역별 Maintainer와 Reviewer를 지정하되 누구나 제안할 수 있습니다.
- **PR 기반 변경**: 작은 기능 브랜치, 자동 검증, 리뷰와 결정 기록을 표준으로 사용합니다.
- **문서가 진입점**: README, CONTRIBUTING, API 명세, 아키텍처, 트러블슈팅과 ADR을 최신으로 유지합니다.
- **안전한 공유**: 최소 권한, 비밀 검사, 의존성 검토와 데이터 분류를 병합 조건에 포함합니다.

## 역할

| 역할 | 책임 |
|---|---|
| Sponsor | 목표·자원 승인, 팀 간 장애 제거 |
| Maintainer | 로드맵·품질 기준·릴리스·최종 병합 책임 |
| Trusted Committer | 반복 기여, 이슈 분류, 리뷰와 멘토링 |
| Contributor | 이슈 제안, 기능 브랜치 구현, 테스트·문서 작성 |
| Security/Legal Reviewer | 민감정보, 라이선스, 개인정보 및 보안 고위험 변경 검토 |

## 단계별 계획

### 0단계 — 준비와 기준선 (1~2주)

- 저장소 공개 범위와 데이터 분류를 확정합니다.
- `LICENSE`, `README`, `CONTRIBUTING`, `CODE_OF_CONDUCT`를 기준 문서로 지정합니다.
- PR·이슈 템플릿, 라벨, CODEOWNERS와 브랜치 보호 정책을 점검합니다.
- 기존 Cycle Time, 외부/타 팀 기여 수, 리뷰 응답시간의 기준선을 수집합니다.

**완료 조건:** 신규 기여자가 문서만으로 환경을 준비하고 작은 문서 PR을 만들 수 있습니다.

### 1단계 — 파일럿 운영 (3~6주)

- 백엔드, AI, 프런트엔드 중 1~2개 팀을 파일럿 참여자로 선정합니다.
- `good first issue`, `help wanted`, `area/*` 라벨로 진입 가능한 백로그를 제공합니다.
- 주 1회 Office Hour와 비동기 Discussion을 운영합니다.
- `[MUST]`/`[SHOULD]` 리뷰 규칙과 리뷰 SLA를 적용합니다.

**목표 지표:** 첫 리뷰 2영업일 이내 80%, 파일럿 타 팀 PR 3건 이상, 문서 기반 온보딩 완료율 80% 이상.

### 2단계 — 확장과 자동화 (7~10주)

- CODEOWNERS, 필수 CI, 비밀·의존성 검사와 승인 규칙을 보호 브랜치에 적용합니다.
- 공통 모듈과 API의 버전·지원 정책을 문서화합니다.
- ADR, 변경 로그, 릴리스 노트를 PR 과정에 연결합니다.
- 반복 기여자를 Trusted Committer로 승급하는 기준을 공개합니다.

**목표 지표:** 필수 CI 통과율 95% 이상, 재작업으로 재개된 PR 15% 이하, 타 팀 재사용 사례 2건 이상.

### 3단계 — 정착과 개선 (11~12주 및 상시)

- 월별 운영 회고에서 병합 소요시간, 리뷰 부하, 기여자 유지율과 재사용 효과를 검토합니다.
- 분기마다 Maintainer·CODEOWNERS·문서 최신성을 점검합니다.
- 장기 미응답 영역은 소유권을 재배정하고 기여 장벽을 제거합니다.
- 공개 OSS로 환원 가능한 개선을 선별해 upstream 기여합니다.

**완료 조건:** 운영 지표의 담당자와 정기 검토 주기가 지정되고, 두 개 이상의 팀이 독립적으로 기여합니다.

## 협업 흐름

```text
아이디어/문제 발견
  -> Issue 또는 Discussion에서 범위 합의
  -> 기능 브랜치와 Conventional Commit
  -> 테스트·문서·보안/라이선스 점검
  -> CODEOWNER 리뷰 및 CI
  -> main 병합·릴리스·회고 지표 반영
```

## 측정 지표

| 범주 | 지표 | 초기 목표 |
|---|---|---|
| 참여 | 월간 활성 기여자, 타 팀 PR 수 | 분기별 증가 추세 |
| 흐름 | 첫 리뷰 시간, PR Cycle Time | 첫 리뷰 2영업일 이내 |
| 품질 | CI 성공률, 롤백·재오픈 비율 | CI 95% 이상 |
| 재사용 | 공통 모듈 소비 팀, 중복 제거 사례 | 파일럿 후 2개 팀 이상 |
| 지속성 | 문서 최신성, Maintainer 편중도 | 분기 점검 100% |

숫자는 사람의 순위를 매기는 용도로 사용하지 않습니다. 병목과 기여 경험을 개선하는 팀 단위 신호로만 활용합니다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| Maintainer 리뷰 병목 | 영역별 CODEOWNER 확대, 리뷰 당번과 SLA 운영 |
| 기여 품질 편차 | 작은 이슈, 예제 PR, 자동 검사와 멘토 지정 |
| 민감정보 노출 | 사전 데이터 분류, 비밀 검사, 최소 권한, 사고 대응 절차 |
| 라이선스 충돌 | 의존성 승인 체크리스트와 정기 SBOM/고지 검토 |
| 내부 fork 확산 | upstream-first 원칙, 공통 변경의 원 저장소 PR 우선 |

## 12주 후 의사결정

Sponsor와 Maintainer는 목표 지표, 보안 사고, 유지보수 부하와 재사용 성과를 검토해 확대·보완·중단을 결정합니다. 결정과 배경은 ADR로 남기고 다음 분기 로드맵에 반영합니다.
