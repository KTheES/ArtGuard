# STEP 26 감사 기록

기존 operational_audit 기록을 조회하는 관리자 API와 누락된 주요 이벤트를 추가했습니다. 관리자 역할은 JWT와 현재 DB 계정 상태에서 모두 검사합니다.

`GET /api/v1/admin/audit-events?limit=50&beforeId=100&subjectUserId=UUID&resourceType=LOGIN`

필터는 모두 선택 사항입니다. limit는 1~100, beforeId는 양수입니다. id 내림차순으로 반환하며 다음 요청에는 응답의 nextBeforeId를 그대로 전달합니다. null이면 해당 조회 시점에 더 오래된 결과가 없습니다. offset 방식과 달리 위쪽에 새 이벤트가 추가돼도 이미 읽은 행을 반복하지 않습니다. 다만 장기 트랜잭션이 나중에 커밋한 과거 ID까지 고정하는 스냅샷 내보내기는 아닙니다. 새 이벤트 확인은 첫 페이지에서 다시 시작합니다. 사용자당 조회는 분당 30회입니다.

## 기록 범위

- LOGIN: 비밀번호 확인과 토큰 저장이 성공한 로그인 처리. 실제 응답 수신까지 보증하지 않습니다. 실패한 로그인은 성공 이벤트로 기록하지 않습니다.
- ARTWORK_CREATED / ARTWORK_UPDATED / ARTWORK_DELETED: 생성, 제목·설명·모니터링 변경, 소프트 삭제. 본문 대신 상태·버전만 저장합니다.
- EMAIL_VERIFICATION: 이메일 인증 여부 변경. 이메일 주소·코드는 저장하지 않습니다.
- 기존 SUBSCRIPTION, DETECTION_REVIEW, TAKEDOWN_REPORT, OWNERSHIP_CLAIM, OWNERSHIP_SOURCE_FILE, SOCIAL_ACCOUNT_CHECK: 기존 상태 전이 및 검토 기록을 그대로 조회합니다.
- ADMIN_AUDIT_READ: 관리자 감사 기록 조회. 조회 결과를 읽은 뒤 현재 관리자의 조회 사실을 기록합니다.
- SOURCE_FILE_DOWNLOADED: 관리자 원본 다운로드 권한·해시 검사 후 파일 응답을 준비한 사실. 실제 네트워크 전달 완료를 뜻하지 않습니다.

로그인·조회·다운로드의 앱 기록은 고정된 이벤트 enum과 사용자·행위자·대상 UUID만 받습니다. 비밀번호·토큰·이메일·파일 바이트·IP·User-Agent·자료 설명을 전달하지 않습니다. 기존 검토 이벤트의 actorId는 유지하지만 과거 이벤트나 DB 트리거만으로 행위자를 알 수 없는 이벤트에 소유자를 행위자로 추정해서 넣지 않습니다. subjectUserId는 관련 사용자이며 항상 실제 행위자는 아닙니다.

## 일관성과 제한

작품·인증 상태 감사 트리거는 해당 변경과 같은 DB 트랜잭션에서 처리합니다. 관리자 조회·다운로드는 감사 기록 실패 시 응답을 반환하지 않습니다. 로그인은 Redis 토큰 저장과 PostgreSQL 감사 기록을 하나의 원자적 트랜잭션으로 묶지 않으므로, 감사 DB 오류가 나면 응답이 실패하더라도 Redis 세션은 교체됐을 수 있습니다.

기존 감사 테이블의 수정·삭제 차단 트리거를 유지합니다. 이는 DB 슈퍼유저·트리거 비활성화까지 막는 암호학적 변조 방지는 아닙니다. WORM 외부 보관·서명·보존기간·삭제 정책·외부 로그 전송은 별도 운영 항목입니다. 모든 HTTP 요청, 실패 로그인, 카탈로그 수집 실행 등 모든 관리자 행위를 자동 수집하는 범용 감시 기능도 이번 범위에 포함하지 않습니다.

## 검증 및 다음 단계

단위 테스트는 관리자 접근 제한·권한 철회·필터 입력·조회 감사 실패 처리 및 로그인 성공/실패 구분을 검증합니다. PostgreSQL 통합 테스트에는 V25 트리거, 개인정보 본문 제외, 커서·필터와 불변성을 포함했습니다. Docker 연결이 없어 DB 통합 실행은 미완료입니다.
