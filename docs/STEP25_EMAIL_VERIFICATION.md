# STEP 25 이메일 인증

로그인한 계정의 현재 등록 이메일을 확인합니다. 인증 요청·상태 조회·코드 제출은 모두 JWT 인증이 필요합니다. 이메일 주소나 사용자 ID를 요청으로 지정할 수 없습니다.

- `GET /api/v1/auth/email-verification`: `data.verified` 조회
- `POST /api/v1/auth/email-verification/request`: 인증 메일 요청
- `POST /api/v1/auth/email-verification/confirm`: `{"token":"메일에 있는 인증 코드"}` 제출

코드는 난수 32바이트를 URL-safe Base64로 표현한 43자이며 30분간 유효합니다. DB에는 SHA-256만 저장하고 API 응답에 코드를 포함하지 않습니다. 코드가 URL·접근 로그에 남지 않도록 본문으로 제출합니다. 본문 로깅은 운영 환경에서도 사용하지 않아야 합니다. 화면은 아직 없으므로 API 클라이언트가 필요합니다.

사용자 행 잠금과 트랜잭션으로 재발송·인증을 직렬화합니다. 재발송은 5분 간격이며 이전 코드를 무효화합니다. Redis 요청 제한은 사용자당 요청 1회/분, 확인 5회/분입니다. 이미 인증된 계정의 발송 요청은 메일을 보내지 않습니다. 사용한 코드 재제출, 만료, 다른 계정의 코드는 거절합니다. 이메일 변경 시 DB 트리거가 인증 상태와 남은 코드를 초기화합니다.

## 설정과 영향

기본적으로 실제 발송은 꺼져 있습니다. `EMAIL_VERIFICATION_ENABLED=true`, 기존 `NOTIFICATION_ENABLED=true`, `NOTIFICATION_FROM`, SMTP 설정이 필요합니다. 기존 SMTP 게이트웨이를 사용하므로 NOTIFICATION_ENABLED는 기존 탐지 알림 작업도 활성화합니다. 운영 발송은 해당 알림까지 검토한 뒤 설정해야 합니다. 이번 개발에서는 실제 메일을 보내지 않았습니다.

메일은 요청 트랜잭션 중 동기 발송합니다. 발송 오류는 토큰 변경을 롤백하고 일반화된 503 오류를 반환합니다. SMTP 접수 후 DB 커밋 실패나 SMTP 응답 유실 시 받은 코드가 유효하지 않을 수 있으므로 재요청해야 합니다. 별도 내구성 메일 큐는 이번 범위에 포함하지 않았습니다.

V21 적용 후 기존 사용자를 자동 인증 처리하지 않습니다. 신고 초안 생성·제출 기록에는 이메일 인증이 필수입니다. 설정이 꺼져 있고 미인증 상태라면 해당 작업은 인증 설정을 완료할 때까지 차단됩니다. 로그인·작품 등록 및 기존 신고 조회는 계속 가능합니다. 이메일 접근 확인은 작품 소유권 확인을 의미하지 않습니다.

## 검증 및 다음 작업

단위 테스트는 코드 해시 저장, 등록 이메일 수신자 고정, 비활성 발송·쿨다운·SMTP 오류 처리, 인증·신고 제한, 인증 경로와 요청 제한을 검증합니다. PostgreSQL 통합 테스트는 재발송·만료·다른 사용자·일회용·이메일 변경을 포함합니다. Docker 부재로 통합 테스트 및 V21 실DB 검증은 미완료이며 실제 SMTP 수신 검증도 남아 있습니다.

선택적 소유권 자료 제출·검토 API는 [별도 문서](STEP25_OWNERSHIP_REVIEW.md)에 정리했습니다. [소셜 프로필 통제 확인](STEP25_SOCIAL_ACCOUNT_CHECK.md)과 [원본 파일 첨부](STEP25_SOURCE_FILES.md)도 추가했습니다. 다음 개발 항목은 STEP 26 감사 로그입니다.
